## Failures and classification
Classification is my reading of the evidence. "UNSURE" means the evidence does not settle whether the test or the product is at fault.

1. **test_w26a_same_size_same_mtime_corruption_is_caught_by_the_weekly_audit** (card L1). Failing assertion: `no FAILURE mail for the audit divergence: ['ACTION_REQUIRED']`.
   - L1 premise verified in this run: after the baseline, the NAS and cloud copies had the same mtime as the source, and the corruption landed (same size, different MD5).
   - The weekly audit did detect the divergence on both legs (`VERIFICATION_FAILED`, names `Tax/a.xlsx`).
   - Only the alert kind differs: the test expects FAILURE, the product sent ACTION_REQUIRED.
   - Classification: **UNSURE** (test expectation vs product's choice of alert kind). Needs a plan check.

2. **test_l2_unicode_case_normalization_churn** (card L2). Failing assertion: the NAS listing `Ledger.xlsx` differs from the source listing `LEDGER.xlsx` after a case-only rename.
   - The rename itself was done and checked; the NAS keeps the old-case name. The `café.txt` duplicate (NFC/NFD) is listed identically on both sides.
   - Classification: **probably product/tool behaviour, not the rig** (robocopy does not change the name case of an existing NTFS destination entry). Low severity (name case only). Severity is an owner call. The cloud leg's name was not part of the failing assertion.

3. **test_w26c_L4_file_growing_during_upload** (card L4). Expected CLOUD_SUSPECT or CLOUD_PARTIAL; got **CLOUD_FAILED**. rclone exit 6: "source file is being updated (size changed ...)". rclone reported IO errors and did not delete anything.
   - Classification: **UNSURE** (status taxonomy: the product maps this rclone exit to CLOUD_FAILED; the test accepts only SUSPECT/PARTIAL). No data loss seen.

4. **test_w26c_L5_exclusively_locked_file_cloud_leg** (card L5). Same pattern: rclone exit 1, "being used by another process", got **CLOUD_FAILED**, expected SUSPECT/PARTIAL. Same classification as L4: **UNSURE**.

5. **test_w26e_L7_acl_denied_subfolder_without_backup_mode** (card L7). Failing point: the test's own `finally` cleanup, `icacls /remove:d` on the denied `Audit` folder returned "Access is denied" (exit 5).
   - Product behaviour looked right in this run: the cloud guard measurement failed (rclone size exit 6, access denied), the cloud leg was not COMPLETE, and the run ended with errors.
   - Because the cleanup assertion raised first, the assertions after it were **not reached**, including the L7 cloud assertion (`latest.get("cloud") not in COMPLETE`). That assertion is weak by design: it accepts any non-COMPLETE status, including FAILED. This is from reading the code; it was not exercised.
   - Classification: **TEST RIG** (the cleanup cannot remove the deny ACE it set; needs an owner-based reset or takeown).

6. **test_lc2a_junction_at_fy27_28_is_never_a_silent_false_success** (card LC2a). Outcome recorded by the test: `UNACCEPTABLE`. Cloud and LAN run rows for FY27-28 are empty, there is no activation row, and no FY27-28 mail.
   - The product refused the junction and logged one INFO line: "FY overlap activation: deferred (FY27-28): ... is a shortcut (link), not a real folder, and the backup refuses to use it".
   - It was not a false success. But by the test's rule (adopted and converged, or a BLOCKED/failure row plus a mail), a refusal with no row and no mail counts as silent.
   - Classification: **PRODUCT, medium confidence**, needs an owner decision on whether a refused junction must record a row and send a mail (the fail-closed rule suggests it should be visible).

The other 8 tests passed: L3, the four w26d guard tests, the LC1 best-case test, and LC2b, LC2c, LC2d.
