The calendar then has to implement what the product really does on a switch-due day (all of it is in `calendar.py` `build_calendar`, ROLLOVER_CHECK branch at line 373):

1. Switch-due day and `clock_unproven` (X02): no finals, no archive, no config change. The next day (no override) falls into the normal `d >= sw` path, so the switch lands on 04-02 06:00 automatically.
2. Switch-due day and `cloud_down` without `clock_unproven` (X03): rows `rollover` `ROLLOVER_BLOCKED`, `...-rollover-final-cloud` `CLOUD_FAILED`, `...-rollover-final-lan` `LAN_COMPLETE`; mail ACTION_REQUIRED key `blocked:rollover`, AAM-ROL-02, plus the final cloud failure mail is suppressed (same key within 12 h), so add nothing for it.

## P findings (product, plain language)

P1 Escalation mail is dropped (known, F-P1-ESCALATION-SUPPRESSED, still reproduces). On the first morning of a blocked activation the office gets a WARNING; the next morning's stronger "ACTION NEEDED" reminder is silently dropped because the daily check started 5 ms short of 24 h. notifications id 5 (dev54): `rollover:activation:FY91-92` ACTION_REQUIRED SUPPRESSED "same alert already sent at 2090-12-31T06:00:01.207 (cooldown 24h)", this one at `2091-01-01T06:00:01.202`. Impact: the reminder promised in the plan never arrives on roughly every second try with a daily cron, so a 3-day wait for activation looks like silence after day 1. Direction: never let the cooldown swallow an escalation to a higher kind, and/or compare with a minute of tolerance (`core/notify.py:~668`).

P2 A real internet outage is mailed as "Google refused the login" (new, X01/X02/X03). With the cloud unreachable the office gets `PROBLEM ... Google Cloud refused the login (AAM-CLD-03)`: "the backup's key (expired, deleted or permissions removed)... The cloud key must be renewed. Forward this to support." Evidence: dev54 mail 0001, dev51 mail 0002; log text `oauth2: cannot fetch token: Post ".../token": dial tcp 127.0.0.1:9: connectex: ... actively refused`. `core/rclone_errors.py` tests TLS, DNS, then AUTH (`oauth2: cannot fetch token|invalid_grant|401|403...`) BEFORE NETWORK (`dial tcp|timed out|network is unreachable...`). Any failure while fetching the token (route down, firewall, unplugged cable with cached DNS) therefore wins as AUTH. Only a failure that also contains `no such host` is classified DNS. Impact: on a genuine outage the firm is told to renew a key, not "check the internet", and the day-0 reaction (support call, key reissue) is wrong. Caveat: the harness blackhole is a refused local port, so the exact real-world text depends on DNS state, but the ordering defect is visible in the code. Direction: classify `oauth2: cannot fetch token` as AUTH only when the same line carries 400/401/invalid_grant, otherwise let the NETWORK/DNS pattern win. (The dev43 diagnosis saw AAM-CLD-10 for the same injection; the product now answers CLD-03, so the text moved since.)

P3 New-year folder blocked by the mass-delete guard (known F-NEW-G3-SMALL-N, now seen on the live year). After the switch, FY91-92 is the only year in use and holds about 5 files; deleting 2 of 5 (40%) is above the 10% limit, so BOTH legs stop with AAM-DEL-01 "Backup would delete many files... Blocked by: G3_MASS_DELETE", approval request open, and every night sends another ACTION NEEDED mail (04-02 02:01, 04-02 21:01, 04-03 02:01, 04-03 21:01: `blocked:cloud:FY91-92`, `blocked:lan`, `blocked:cloud`, `blocked:lan`). Impact: right at the start of a year (when the folder is smallest because the office has only just begun to use it) a single deleted or renamed file stops all backups of the year in use until someone approves on the dashboard; the watchdog turns red (stale lan, stale cloud by 04-03). Nothing is lost, the old year is safely closed, but the new year is unprotected for days. The 10% rule has no minimum count (it allows `min(500 files, 10% of files)`, so 0 files for up to 9 files). Owner decision needed: floor such as "up to N files may always be deleted" (config key, bounds) or a looser percent rule while the folder is small. The harness side (F5) only stops provoking it.

P4 Rollover also switches while the new year's backup is blocked (observation tied to P3). On 04-02 06:00 `ROLLOVER_COMPLETE` ran although `cloud FY91-92` was `CLOUD_BLOCKED` at 02:01 the same morning.
